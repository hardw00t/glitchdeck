# v2.2.2 release notes

- `dup-webhook` now supports simultaneous `concurrent` delivery and `timeout_retry` after an upstream attempt, in addition to the unchanged default stagger. Replays share the buffered request body, respect the same egress policy, and report status counts, outcomes, and capacity skips.
- `ws-glitch` can target `data`, `control`, or `all` frames. `all` remains the default; `data` leaves Close, Ping, and Pong untouched and excludes them from `after_frames` and `every`.
- The WebSocket proxy sends Close `1009` for payloads over 4 MiB and `1002` for malformed frames. These errors appear in wire events and reports. Intentional `close_1006` still simulates a silent disconnect.
- CLI and MCP validation reject invalid mode, frame class, range, and parameter combinations without changing the tape schema.

## Release review fixes

- Concurrent delivery counts as applied only when a copy clears egress policy. Denied and canceled copies remain visible even when no fault applies. Closing the proxy waits for admitted copies to settle.
- `timeout_retry` reserves the entire retry group before substituting a sender failure. If capacity is insufficient, the client gets the ordinary upstream result. Default sequential mode keeps legacy partial admission and staggered timing. When replay labels are enabled, the original never forwards a sender-supplied replay marker.
- Reports expose only the fixed replay-capacity skip reason on webhook fault rows. MCP exposes replay and frame diagnostics and advertises fault parameters without closing the `params` object.
- The WebSocket proxy rejects malformed headers before waiting for their payload, records known lengths and timestamps, and closes both peers if cancellation races error handling. The frame fuzzer exercises both production pumps.

## Local smoke tests

| Scenario | Observed result |
| --- | --- |
| Python receiver with a non-atomic check and insert | `HTTP 200`, `rows=5`, replay status `200×4`. |
| Python receiver with a locked check and insert | `HTTP 200`, `rows=1`, replay status `409×4`. |
| Timeout after commit | `curl --max-time 1` printed `glitchdeck: simulated sender timeout after upstream commit HTTP 504`; `rows=1`, `retries=1`, `committed_status=200`. |
| Reset after commit | curl exited `56`; `rows=1`, `retries=1`, `committed_status=200`. |
| 100 simultaneous webhook senders | `originals=100`, `sent=64`, `capacity_exceeded=136`, `replay_capacity_exceeded=68`, one warning. |
| Python WebSocket server, `ping_interval=0.05` | Ten runs each dropped `data_seq=3`; Node received `[1,2,4,5,6]`. |
| Oversized WebSocket frame | Node reported `1009 glitchdeck: frame exceeds 4 MiB proxy limit`; the upstream received masked Close `1009`; the report recorded `declared_bytes=4194305`. |

All 43 bundled tapes validated. The 37 existing tapes matched their v2.2.1 exit codes and JSON after excluding only elapsed duration and the new `dup-webhook` replay statistics. The six new tapes matched their expected exits.

The Go race run reproduced the double insert in `20/20` trials. The p95 RoundTrip start delta was `0 ms` at millisecond resolution, the largest receiver arrival spread was `1.79 ms`, and the 100-sender test peaked at 64 pending copies.

During overlapping race and fuzz runs, the unchanged SSE test `TestDecodedLimitsStopReadingUpstream/flate/truncated=false` exceeded its source-write bound once (`2162688` bytes). The subsequent isolated `go test -race -count=1 ./...` passed in every package. No SSE code or test was changed. All six fuzz targets completed 15-second campaigns; formatting, vet, and the Node model tests passed.
